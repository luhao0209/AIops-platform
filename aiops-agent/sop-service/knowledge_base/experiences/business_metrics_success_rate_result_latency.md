# 业务指标速查：成功率 / 结果分布 / 延迟

## 适用范围
用于业务侧异常：下单成功率下降、超时变多、用户反馈失败或变慢。
不用于先解释节点 CPU / Load / 磁盘 IO（那走系统指标文档）。

## 成功率指标
### 作用
反映业务请求整体是否成功，是“出没出问题”的总览信号，不能单独当根因。

### 典型现象 → 可能问题
- 成功率明显下降 → 可能是系统性失败（timeout 等），也可能是业务性失败（如 duplicate_order、规则拒绝）

### 应该怎么查
1. 先调 `get_business_overview`，看总量、成功数、失败分布
2. 再调 `get_metric_trend`（或受控意图 `business_result_trend`），看近 30m～2h 成功率与各 result 趋势

### 结果怎么读
- 成功率低但失败以业务码为主 → 偏业务规则 / 幂等 / 重试，不优先当基础设施故障
- 成功率低且 timeout 占比升高 → 偏链路超时，进入延迟与依赖路径
- 样本很少（低流量窗口）→ 标注证据弱，不和高峰期强对比下结论

### 查不到时
说明业务指标无数据或查询失败，只写证据不足；不要用节点 CPU 正常去推断“业务也正常”。

## 结果分布（result）
### 作用
把“失败”拆开：看是超时、重复订单，还是其它业务结果，决定后面走系统路径还是业务路径。

### 典型现象 → 可能问题
- duplicate_order 等业务结果激增 → 可能是重试/幂等/前端重复提交，不一定是宕机
- timeout 结果激增 → 可能是网关到下游慢、下游不可达、或依赖拥堵

### 应该怎么查
1. 以 `get_business_overview` 的失败分布为第一证据（多数情况先够用分流）
2. timeout 占主导、需要按服务看请求量/错误率时：可试 `get_service_golden_signals`（须填对真实 service 与 namespace；它不是万能延迟探针，见下文）
3. 黄金信号无样本、服务名对不上、或仍不足：改用 `get_metric_trend` 查已知业务/网关相关指标，并可用 `search_logs`（关键字 `timeout` / 相关错误码）
4. 同窗口可调 `search_change_events` 核对是否有发布或配置变更

### 结果怎么读
- 业务码主导 → 先解释业务机制，再决定要不要查节点资源
- timeout 主导 → 先分清「已有错误/超时证据」再决定是否看依赖；依赖可疑时可查 `get_infrastructure_saturation`，不是必查项
- 多种 result 同时恶化 → 先看变更时间线，再扩大排查面

### 查不到时
没有 result 标签或指标缺失时，不要猜测失败类型；只说明无法区分业务失败与系统失败。

## 延迟 / 请求错误（timeout 路径）
### 作用
在 timeout 占主导时，补充「哪个服务请求/错误在恶化」；有延迟指标时再看是否变慢。目标是拿证据，不是绑定某一个固定命令。

### 典型现象 → 可能问题
- 成功率下降且 timeout 增多 → 可能是服务变慢、下游慢、或依赖饱和

### 应该怎么查（优先候选，不是唯一口令）
目标：拿到异常窗口内的请求量、错误率；若环境有延迟指标再看延迟。

1. 失败分布已能说明 timeout 主导时，不必强行再调一轮服务工具，可直接进入变更/日志/依赖
2. 需要按服务看请求/错误时，可试 `get_service_golden_signals`：
   - 前提：指标带正确的 `service`、`namespace` 标签；填错会得到空样本
   - 限制：默认偏业务请求计数；延迟直方图未配置时没有可用 P95，不能当成通用 HTTP 延迟探针
3. 上一步无样本或不适用时：改用 `get_metric_trend` 查已知相关 PromQL，或 `search_logs` 查 timeout
4. 依赖侧可疑（非必须）：可查 `get_infrastructure_saturation`（node / mysql / redis）作饱和度旁证

### 结果怎么读
- 请求错误升高（或确有延迟升高）→ 偏服务或下游问题，继续沿调用链，仍标证据层级
- 黄金信号空样本 → 只说明该 service/namespace/窗口下无有效样本或标签未命中，不能说“服务一定健康/已排除”
- 基础设施饱和高且与 timeout 同期 → 可作依赖侧推断，不能单凭饱和度定根因

### 查不到时
先纠正对象（服务名、namespace）或换 `get_metric_trend` / 日志；禁止在空结果上写“已排除服务异常”。

## 不要误判
- 禁止只凭成功率一个数断言“系统故障”或“根因是某某节点”
- 业务性失败不要先套 CPU / 磁盘 IO 故事
- 本篇只处理业务指标；机器变慢但业务指标正常时，转系统指标文档
